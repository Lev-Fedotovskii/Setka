# DD-001 — Schedule ingestion & canonical model

**Status:** Draft 0.1  
**Date:** 2026-09-02  
**Scope:** v1.0  
**Decision owner:** project `сетка`

## 1. Goal

Convert university timetable sources (starting with MIPT Excel workbooks) into one deterministic canonical representation that can drive:

- the “Today” screen;
- the academic week grid;
- notifications;
- free-window calculation;
- homework planning and recommendations;
- ICS export;
- future source updates and diffs.

The canonical representation is the source of truth inside the app. Excel, LMS and ICS are adapters around it, not the core format.

## 2. Confirmed MIPT assumptions

For the 2026/2027 academic year MIPT publishes a timetable for the autumn semester and explicitly treats the first teaching week as odd.

From 2026-09-01 the official lesson grid is:

| Pair | Start | End |
|---:|---:|---:|
| 1 | 09:00 | 10:25 |
| 2 | 10:35 | 12:00 |
| 3 | 12:10 | 13:35 |
| 4 | 13:55 | 15:20 |
| 5 | 15:30 | 16:55 |
| 6 | 17:05 | 18:30 |
| 7 | 18:40 | 20:05 |

The importer MUST NOT hard-code these values globally. They belong to a versioned `bellSchedule` for an institution/semester.

MIPT group identifiers can include suffixes and variants (examples in university documents include `Б01-501`, `Б02-402к`, `Б01-205а`, `С01-119`). Group recognition therefore cannot assume one exact format.

## 3. Core architectural decision

```text
Source
  ↓
SourceAdapter
  ↓
Workbook / Source IR
  ↓
Layout inference
  ↓
Semantic extraction
  ↓
Candidate schedule
  ↓
Validation + confidence
  ↓
User preview / corrections
  ↓
CanonicalSchedule
```

Supported adapters in order:

1. `mipt-xlsx-local` — user selects a downloaded `.xlsx/.xls` file.
2. `mipt-web` — future automatic retrieval from the timetable page.
3. `mipt-lms` — future structured source if a stable endpoint can be used.
4. `manual` — manual editing/import fallback.
5. `ics` — import/export interoperability, not primary university ingestion.

A browser PWA may be blocked by CORS when fetching university files directly. Therefore v1 must work fully with local file import. Automatic retrieval can later run through a small service or a scheduled repository job, while Tauri can use native networking.


## 3A. MIPT source catalog

The official schedule page is a **catalog**, not the timetable payload itself. The user expands the timetable list and selects a course; that link resolves to a separate `.xlsx` workbook under `https://mipt.ru/upload/...`.

Example source shape:

```text
MIPT schedule page
  ↓
expand timetable list
  ↓
choose school/program + course
  ↓
direct XLSX URL
  ↓
MiptXlsxAdapter
```

Therefore source discovery and workbook parsing are separate modules:

```ts
type ScheduleSourceDescriptor = {
  institutionId: "mipt";
  label: string;                 // human title from the catalog
  academicYear?: string;
  term?: "autumn" | "spring";
  course?: number;
  program?: string;
  url: string;
  contentType: "xlsx" | "xls";
};
```

### v1 acquisition strategy

- **PWA:** the safest flow is `Open MIPT → download workbook → Import file`, because browser CORS/content-disposition rules may prevent reliable direct fetches.
- **Tauri Android/Windows:** the app may fetch the direct XLSX URL natively, outside browser CORS restrictions.
- The import UI must also accept a pasted direct XLSX URL for Tauri builds.

### Catalog strategy

Do not couple the parser to the accordion/DOM structure of the MIPT page. Catalog discovery is allowed to change independently. Preferred options, in order:

1. small versioned `mipt-sources.json` manifest generated from the official page;
2. Tauri-native catalog scraper;
3. manual direct URL / local file fallback.

A static manifest can be regenerated by a scheduled GitHub Action and hosted together with the PWA. That gives all clients a simple, cacheable source list without requiring a permanent application backend.

Example:

```json
{
  "updatedAt": "2026-09-02T00:00:00Z",
  "sources": [
    {
      "label": "БВО · 1 курс · осень 2026–2027",
      "academicYear": "2026-2027",
      "term": "autumn",
      "course": 1,
      "url": "https://mipt.ru/upload/…xlsx",
      "contentType": "xlsx"
    }
  ]
}
```

The manifest stores only official source metadata and URLs. The XLSX remains authoritative.

## 4. Canonical model

The canonical model separates recurring academic events from date-specific exceptions and from user-owned tasks.

```ts
type CanonicalSchedule = {
  schemaVersion: "1.0";

  institution: {
    id: string;
    name: string;
    timezone: string;          // e.g. Europe/Moscow
  };

  term: {
    id: string;
    title: string;
    startsOn: string;         // YYYY-MM-DD
    endsOn: string;
    parityAnchor: {
      date: string;           // date belonging to week #1
      parity: "odd" | "even";
    };
    bellScheduleId: string;
  };

  bellSchedules: BellSchedule[];
  groups: Group[];
  subjects: Subject[];
  instructors: Instructor[];
  locations: Location[];

  series: LessonSeries[];
  exceptions: ScheduleException[];

  importMeta: ImportMeta;
};
```

### Bell schedule

```ts
type BellSchedule = {
  id: string;
  validFrom: string;
  slots: {
    number: number;
    startsAt: string;   // HH:mm
    endsAt: string;
  }[];
};
```

### Recurring lesson series

```ts
type LessonSeries = {
  id: string;

  subjectId: string;
  kind:
    | "lecture"
    | "seminar"
    | "lab"
    | "sport"
    | "practice"
    | "other";

  cohorts: {
    groupId: string;
    subgroup?: string;
  }[];

  recurrence: {
    weekdays: number[];       // ISO 1..7
    parity: "all" | "odd" | "even";
    validFrom: string;
    validTo: string;
    includeDates?: string[];
    excludeDates?: string[];
  };

  time: {
    slotNumbers?: number[];
    startsAt: string;
    endsAt: string;
  };

  instructorIds: string[];
  locationId?: string;

  rawNotes?: string[];

  source: SourceTrace;
  confidence: Confidence;
};
```

### Source trace

Every imported record keeps provenance.

```ts
type SourceTrace = {
  adapter: string;
  sourceId: string;
  sourceVersion?: string;
  workbook?: string;
  sheet?: string;
  ranges?: string[];          // e.g. ["F12:H13"]
  rawText?: string;
  fingerprint: string;
};
```

### Confidence

```ts
type Confidence = {
  overall: number;            // 0..1
  fields: {
    subject?: number;
    groups?: number;
    parity?: number;
    time?: number;
    instructor?: number;
    location?: number;
  };
  warnings?: string[];
};
```

Confidence is not “AI”. It is deterministic evidence quality used to decide what must be reviewed.

## 5. Workbook intermediate representation (IR)

Do not parse an Excel file directly into lessons. First preserve the document structure.

```ts
type WorkbookIR = {
  sheets: SheetIR[];
};

type SheetIR = {
  name: string;
  rows: number;
  cols: number;
  cells: CellIR[];
  merges: MergeIR[];
};

type CellIR = {
  row: number;
  col: number;
  value: string | number | boolean | null;
  normalizedText: string;
  style?: {
    fill?: string;
    fontBold?: boolean;
    alignment?: string;
    borderSignature?: string;
  };
};

type MergeIR = {
  from: { row: number; col: number };
  to: { row: number; col: number };
};
```

For MIPT-style non-standard spreadsheets, merged ranges are semantic evidence: a merged subject across several group columns can mean one shared lecture; a merged cell across two time rows can mean a multi-pair lab.

Use an XLSX library that preserves merged cells and enough style metadata. Styles are hints only; correctness must not depend solely on a color.

## 6. Import algorithm

### Phase A — Source acquisition

1. Read workbook bytes.
2. Calculate file hash.
3. Read sheet names.
4. Build `WorkbookIR`.
5. Preserve the original file metadata for debugging.

### Phase B — Normalization

For every cell:

- trim whitespace;
- collapse repeated spaces;
- normalize non-breaking spaces;
- normalize `9.00`, `9:00`, `09:00` to one time representation;
- preserve original text separately;
- split line breaks into tokens without losing their cell position;
- normalize common Cyrillic/Latin look-alikes only for matching, never destructively in `rawText`.

### Phase C — Sheet classification

Score each sheet for timetable likelihood using deterministic features:

- weekday tokens (`понедельник`, `пн`, etc.);
- pair numbers 1–7;
- known lesson times;
- repeated group-like identifiers;
- subject-like text;
- room-like text;
- teacher-like initials/surnames;
- repeated grid structure.

Sheets below a threshold are ignored but remain visible in an “Other sheets” import debug panel.

### Phase D — Layout inference

Infer one of the common layouts:

```text
A. groups are columns, day/time are rows
B. groups are rows, day/time are columns
C. one sheet per group
D. one sheet per school/course
E. mixed block layout
```

Do not implement separate hard-coded parsers for every workbook revision. Represent the inferred axes:

```ts
type Layout = {
  groupAxis: AxisMap;
  dayBlocks: DayBlock[];
  slotAxis: SlotMap;
};
```

Evidence priority:

1. explicit group header tokens;
2. weekday labels;
3. official bell times / pair numbers;
4. merged-cell geometry;
5. style/border changes.

### Phase E — Group expansion

A cell may refer to:

- one group: `Б01-501`;
- several explicit groups;
- a range: `Б04-401-406`;
- a group + suffix;
- a subgroup marker;
- “all groups” implied by a merged header.

Store canonical IDs but preserve the raw label.

Range expansion is allowed only when prefix and numeric pattern are unambiguous. Otherwise flag for review.

### Phase F — Cell semantic extraction

For every semantic timetable region, extract candidates:

```ts
type LessonCandidate = {
  subject?: string;
  kind?: string;
  groups: string[];
  subgroup?: string;
  parity?: "all" | "odd" | "even";
  instructors: string[];
  room?: string;
  day?: number;
  slots?: number[];
  explicitStart?: string;
  explicitEnd?: string;
  rawText: string;
  evidence: Evidence[];
};
```

Use multiple token recognizers, not one giant regex.

Recognizers:

- weekday;
- group/group range;
- parity;
- pair number/time;
- room/building;
- lesson kind;
- instructor;
- URL/online location;
- residual text → likely subject/title.

Residual text is important: after stripping high-confidence metadata, the largest meaningful phrase is usually the subject.

### Phase G — Odd/even week handling

MIPT commonly uses abbreviations around group/subgroup entries. Parity recognition must be contextual and conservative.

Rules:

- explicit terms like `нечет`, `неч`, `нечетная` → odd;
- explicit terms like `чет`, `четная` → even;
- single-letter markers are accepted only when the surrounding sheet/header convention establishes their meaning;
- if the workbook contains a legend, the legend wins;
- if both variants occupy one time slot, create two `LessonSeries`, one odd and one even;
- parity is resolved against the term’s `parityAnchor`, not ISO week-number parity.

This last point is critical: “odd academic week” is not the same thing as an odd ISO calendar week.

### Phase H — Multi-pair and shared events

Merge candidates when all strong semantic fields match and their geometry shows continuity.

Examples:

- a lab spanning pairs 2–3 → one event 10:35–13:35 (or exact explicit times if supplied);
- a lecture merged across five group columns → one series with five cohorts;
- visually repeated duplicate text in merged child cells → one event, not five.

Never merge solely because subject names are equal.

### Phase I — Time resolution

Priority:

1. explicit start/end in source;
2. explicit pair/slot number + versioned bell schedule;
3. inferred position relative to recognized slot rows;
4. unresolved → review required.

If an event spans multiple official slots, use the first slot start and final slot end, preserving any source-specific break semantics only as metadata.

### Phase J — Validation

Hard validation:

- valid weekday;
- start < end;
- referenced groups exist;
- event within term range;
- valid parity;
- no duplicate exact records after normalization.

Soft validation / warnings:

- overlapping events for the same group and parity;
- unknown room;
- unparsed residual tokens;
- event outside official slots;
- conflicting teacher/location across merged geometry;
- suspicious group range expansion;
- low-confidence parity;
- two source records mapping to the same canonical identity with different content.

## 7. Preview UX

Import is not complete immediately after parsing.

```text
Choose source
    ↓
Analyzing workbook
    ↓
Detected groups / semester
    ↓
Choose your group(s)
    ↓
Preview schedule
    ↓
Warnings / uncertain cells
    ↓
Confirm
```

Preview has three review levels:

- **green** — deterministic, no action needed;
- **amber** — parsed but worth checking;
- **red** — unresolved; import cannot silently guess.

Selecting a lesson shows:

```text
Parsed
Math analysis
Mon · pair 2 · odd week
Room 312
Teacher N. N. Example

Source
Sheet "1 course"
Cells F12:H13
"Мат. анализ ..."

[Correct]
```

User corrections are stored as import overrides keyed by a stable source fingerprint, so re-importing a newer workbook can re-apply compatible corrections.

## 8. Stable identity and updates

A timetable is updated during the semester. We need diffable imports.

Generate two identities:

### `sourceFingerprint`
Derived from source document + sheet + geometric region.

### `semanticKey`
Derived from stable semantic fields:

```text
institution
term
groups
weekday
parity
subject-normalized
```

On re-import classify changes:

```ts
type ImportDiff =
  | { type: "added"; after: LessonSeries }
  | { type: "removed"; before: LessonSeries }
  | { type: "moved"; before: LessonSeries; after: LessonSeries }
  | { type: "changed"; before: LessonSeries; after: LessonSeries }
  | { type: "unchanged"; record: LessonSeries };
```

A time/room change should appear as “moved/changed”, not delete + add when semantic identity is strong enough.

User-owned homework and personal planning are NEVER deleted by timetable re-import.

## 9. Imported schedule vs personal layer

Keep two layers:

```text
University layer
- lessons
- sport from university source
- official changes

Personal layer
- manual lessons
- chosen specialization
- homework
- planned work sessions
- personal exceptions
```

The Today screen renders a resolved projection of both layers.

This separation is mandatory for safe re-import.

## 11. Test strategy

The importer is fixture-driven.

For every real workbook revision we keep a small legal test fixture or a sanitized structural fixture and expected canonical output.

Required tests:

- merged lecture across groups;
- odd/even variants;
- group suffixes;
- group ranges;
- multi-pair labs;
- empty cells;
- explicit time overriding slot;
- room/teacher on separate lines;
- duplicate merged cells;
- sheet with unrelated tables;
- changed workbook producing a clean diff;
- low-confidence record entering review instead of silent guessing.

Property tests:

- imported events always have valid intervals;
- parity resolution is stable for a fixed anchor;
- canonical serialization is deterministic;
- re-importing the same source produces zero diff.

## 12. v1 acceptance criteria

The importer is ready for v1 when:

1. A user can choose a real MIPT timetable workbook and their group.
2. The app imports the week without manual re-entry of every lesson.
3. Odd/even week events resolve correctly against academic week #1.
4. The app highlights uncertain rows instead of silently inventing data.
5. The resulting canonical JSON can render Today and Week screens.
6. Re-import of an updated file shows a readable diff.
7. Personal homework/plans survive re-import.
8. Canonical JSON can be exported for debugging and future migration.

## 13. Next implementation spike

Before freezing parser heuristics, run a spike against 3–5 real MIPT workbooks from different schools/courses.

For each file record:

- layout type;
- merged-cell usage;
- parity notation;
- group notation;
- how teachers/rooms are encoded;
- whether colors/borders have semantic meaning;
- known failure cases.

The spike should produce fixtures and only then lock the first MIPT adapter.
